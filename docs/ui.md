# danmubox 前端规格（UI）

> 定位：定义弹幕客户端前端的导航结构、房间页布局、连接状态与手动刷新、消息与身份徽标渲染、礼物栏双模式、输入区与表情面板、举报入口、虚拟列表与滚动、过滤与样式。
> 读者：前端实现者（React + TS）、负责 IPC 与数据层对接的 Rust 侧、验收者。
> 更新时机：新增/修改 IPC 命令或事件（`ipc.md`）、新增 `kind`、调整过滤求值顺序、调整偏好键用法、调整布局断点或待实测校准项时。

本文只描述 UI 层。字段与取值以 [`contract.md`](contract.md) 为准；IPC 命令与事件形状见 [`ipc.md`](ipc.md)；上游协议与发送/举报的实测事实见 [`protocol.md`](protocol.md)；登录与凭据流程见 [`auth.md`](auth.md)；技术栈见 [`decisions/0008-frontend-stack.md`](decisions/0008-frontend-stack.md)。UI **不得**新增 `kind`、字段或偏好键。

**安全红线（契约 §4.1，原样复述）**：`SESSDATA`、`bili_jct`、`DedeUserID` **不得**进日志、不得进前端明文、不得进仓库、不得进崩溃上报。前端消费 `session_status` / `accounts_list` 的登录态与身份字段；唯一的例外是 §2.2.1 的「手填 Cookie」输入框——那是用户主动粘贴，值**只进一次 `account_login_cookie` 调用**：输入框是密码型、提交后立刻清空、不进任何 store 字段、不回显、不写日志、不落偏好文件。

## 1. 技术栈前提

| 项 | 取值 |
|---|---|
| 框架 | React + TypeScript + Vite |
| 虚拟列表 | TanStack Virtual（元素级 `useVirtualizer`） |
| 状态 | Zustand |
| 样式 | CSS Modules（不引入组件库，聊天框自绘）；设计令牌集中在 `app.module.css` 的 `:root`（§9.1） |
| IPC | Tauri 提供的 `invoke` / `listen`（契约 §7 命令与事件） |

不用「行数少时切换为直接渲染」的分支：始终虚拟化，避免两套渲染路径产生行为差异。

## 2. 信息架构与导航

### 2.1 导航结构

导航是两级页面结构：

```
房间列表页 ──(点击房间 / 关注项)──▶ 房间页（可多标签共存）
     ▲                                    │
     └────(返回列表 / 关闭最后一个标签)────┘
```

| 页面 | 内容 | 数据来源 |
|---|---|---|
| **房间列表页** | 账号区（当前身份一行 + 「账号」按钮 → 账号管理对话框，见 §2.2.1）、正在直播（置顶）、我的房间（手动添加）、关注列表（含未开播，分页） | `follow_list` / `rooms_list` / `accounts_list` |
| **房间页** | 标签条、房间头（状态 / 在线 / 看过 / 电池 / `⋯` 菜单）、弹幕列表（唯一生长区）、弹出面板、输入区、礼物栏（可折叠） | `history_query` + `danmubox://message` 等事件 |

当前实现是**单列**：房间列表页与房间页是互斥的两个页面（从列表进房间、从房间返回列表），没有常驻左栏、抽屉或三列。
横向上只区分两档，形态与断点口径见 §9：

| 档 | 宽度 | 形态 |
|---|---|---|
| 宽屏 | > 520px | 单列居中；弹出面板 / 账号对话框 / 房管面板在**文档流**里（展开只挤弹幕列表） |
| 窄屏 | ≤ 520px | 单列铺满（主参考 390×844）；面板同样在**文档流**里（只挤列表、不遮最新一条），只是限高换成视口份额、触屏热区 ≥ 40px；账号对话框是模态，用自底 sheet |

> 早先草案里的 `xs` / `md` / `lg` / `xl` 四档与「常驻左栏 / 抽屉 / 三列」从未实现，已删除，避免与 §9 的断点打架。

### 2.2 房间列表页

自上而下：

| 区块 | 内容 | 排序 / 规则 |
|---|---|---|
| **账号区** | **只占一行**：当前身份（头像 + 昵称 + `uid`；未登录时是「游客态：可接收弹幕，发送需先登录」）+ 一个「账号」按钮，按钮打开**账号管理对话框**（§2.2.1）。下拉、删除、新增、扫码、登出这些控件**不再内联在这一行** | 为什么不做成下拉：**只有一个账号时下拉里只有一项**，会被读成「切换功能坏了」——用户就是这么报的（原话「切换身份的功能好像没法选」）。「有几个账号、各是谁、哪个在用、能对这个账号做什么」四件事装不进一个下拉，所以切换与账号操作全部收进对话框 |
| **添加房间** | 输入短号 / URL / 房间号 → `rooms_add` | 房间不存在时提示「房间不存在或短号无效」并保留输入 |
| **我的房间** | `rooms_list` 中手动添加的房间，带删除按钮（`rooms_remove`） | 上游返回顺序 |
| **关注列表** | `follow_list` 全量（**含未开播**），头像 + 昵称 + 标题 + 状态标签 + 最后开播时间 + 房间号 | 排序：`live_status == 1` 置顶 → `live_start_at` 降序 → `online` 降序 → `room_id` 升序。前端分页，每页 `FOLLOW_PAGE_SIZE = 30`，>1 页时显示上一页/下一页与页码 |

- `live_status` 展示映射：`1` → 「直播中」（强调色）、`2` → 「轮播中」（弱化）、`0` → 「未开播」（弱化）。
- 关注列表里的房间点击即**进场**（打开房间页），不写入 `rooms_list`；「我的房间」的项才走 `rooms_add` / `rooms_remove`。
- 「刷新关注」按钮调用 `follow_list`，刷新期间按钮禁用并显示转圈；失败时保留旧列表并提示原始错误文本。
- **自动加载**：应用启动时（会话就绪后，即 `session_status` 返回且已登录）自动调一次 `follow_list`，
  用户不必手动点刷新；失败同样走上面的错误提示并保留「刷新」按钮，不静默。登录/换号/新建/删除账号后同样重新拉一次。
- 列表项展示头像（`face`）、昵称（`uname`）、真实房间号（`room_id`）、直播状态标签、最后开播时间（`live_start_at`，未知则不显示该段）、关注分组名（有则显示）。
- 直播间标题（`title`）显示在**昵称之后**，超长省略（不撑破行）；上游未给（空串）时**不渲染该元素**，不用占位符顶位。数据来自 `follow_list` 条目自带的 `title`（2026-09-12 实测），不为每个房间另调接口。
- 关注分组来自直播关注接口之外的另一套上游（`protocol.md` A34），因此当前只把上游给到的 `group_name` 显示出来，不自行分组排序。

### 2.2.1 账号管理对话框（`accounts_list` / `account_*`，需求 §2.5）

点账号区的「账号」按钮打开；同一时刻只开一个，`Esc` 或点背景关闭。打开时先重拉一次 `accounts_list`
（用户可能刚在别处登过号，列表必须说当下的事实）。

**概念**：一个**账号** = 一份具名凭据（底层是 `config.toml` 的一条 profile，界面与文档统一叫「账号」）。
**游客态不是账号**：没有凭据就没有条目。`Account` 的字段（`name` / `nickname` / `uid` / `face` /
`logged_in` / `active`）由后端从凭据读出，界面不自己推断谁登录了。

| 区域 | 内容 | 规则 |
|---|---|---|
| 账号行 | 头像 + **昵称** + `uid` + 账号名 + 状态 + 操作按钮 | 一行一个账号。状态三选一：`已登录 · 当前`（强调色边框标出）/ `已登录` / `未登录`（Cookie 失效也落在这里，界面不猜原因）。**昵称与 uid 必须露出来**——「要覆盖/删除的是谁」不能靠用户自己理解账号名 |
| 操作 | `切换`（非当前项才有）/ `重新登录` / `退出登录`（`logged_in` 时才有）/ `删除` | 具体见下表 |
| `＋ 添加账号` | **默认入口**。点了直接出二维码，**不先起名字** | `account_qr_start()` 不带 `target`：扫完由后端按昵称自动命名（重名加后缀）并落盘，列表随即多一行且标为「已登录 · 当前」。**这条路永不覆盖任何已有凭据**——它是「我不想丢原来那个号」时的入口 |
| 二维码面板 | 后端离线渲染的 SVG + 状态文案 + `重新获取` / `关闭二维码` | 2 秒轮询 `account_qr_poll`；文案：待扫「请用 B 站客户端扫码」→ 已扫「已扫码，请在手机上确认」→ 确认（面板收起，列表刷新）→ 过期「二维码已过期，请重新获取」。**发起失败或轮询出错时面板留在原地并给出「重新获取」**，不静默消失 |
| `高级：手填 Cookie` | 折叠入口（需求 §2.5 三种方式之一） | Cookie 输入框为密码型；账号名可留空（`account_login_cookie(cookie, name?)`，缺省时后端按昵称自动生成）。提交后立刻清空输入框；值不进 store、不回显、不写日志 |
| 游客态 | 退出登录即回到游客态 | 条目保留（`logged_in=false`），可随时重新扫码或手填 Cookie 回来 |

| 操作 | 调用的命令 | 二次确认与后果说明 |
|---|---|---|
| 切换 | `account_switch(name)` | 不需要确认。切换后后端用新凭据重建各房间连接，界面重拉 `session_status` / `accounts_list` / `rooms_list` / `follow_list`，并刷新「当前」标记 |
| 重新登录（**覆盖路径**） | `account_qr_start(target)` | **必须确认**，确认条写明「会用新凭据**覆盖**该账号（`name`）现有的凭据，原凭据无法恢复」，确认后才发命令。二维码面板上另有一行同样口径的警示 |
| 退出登录 | `account_logout(name)` | **必须确认**，文案说明「清掉该账号凭据、界面回到游客态；账号条目保留，可随时重新扫码」 |
| 删除 | `account_remove(name)` | **必须确认**，文案说明「条目与凭据一并删除、不可恢复」；删的是当前账号时补一句「会自动切到另一个账号」。**只剩一个账号时按钮置灰**并给出 `title`（后端也会拒） |

**为什么「覆盖」必须显式确认**：这不是假想风险。旧界面上「扫码登录」的语义就是「重新登录、覆盖当前账号的凭据」，
用户拿它登新号，把原账号的凭据直接顶掉了。所以新交互里「添加」与「重新登录」是**两个不同的动作**：
前者永不覆盖，后者先确认、且确认条上写清覆盖的是哪个昵称/账号名。

### 2.3 房间页与多标签

房间页只有**一条纵向生长轴**（用户 2026-09-12：参照官方 web 直播栏重排）。各区域职责固定：

```
[标签条：房间]
[房间头：返回 · ●状态 · 标题 ······ 在线 x · 看过 x · 电池 x · ⋯]
[弹幕列表  ← 唯一的 flex-1 生长区与滚动区]
[弹出面板（表情 / 短语 / 筛选）← 在输入区上方、向上展开，列表随之变矮并重新贴底]
[输入区：输入框 + 工具行（表情 短语 筛选 …… 发送）]
[礼物 / SC 栏 ← 在输入区下方，全宽，可折叠]
```

| 区域 | 为什么在这里 |
|---|---|
| 弹幕列表 | 唯一会生长/滚动的区域；其它区域展开只会挤它，**不会盖住最新弹幕** |
| 弹出面板 | 面板是文档流里的一块（不是浮层），展开时列表上弹；跟随模式下重新贴底 |
| 房管面板 | 与弹出面板同层（输入区上方），由房间头 `⋯` 菜单开合；展开时同样只挤压弹幕列表（§4.9） |
| 输入区 | 贴底；工具行在输入框下方、发送在右 |
| 礼物栏 | 从「右侧竖栏」改为输入区下方的全宽折叠条：**把宽度还给弹幕**（`ui.gift_panel_mode = separate` 时才出现） |

线框（`xl`，`ui.gift_panel_mode = separate` 且礼物栏展开）：

```
┌──────────────────────────────────────────────────────────────┐
│ [● 1号房 ×][○ 2号房 ×][ + ]                                   │
├──────────────────────────────────────────────────────────────┤
│ 返回  ●  1号房主播               在线 1.2万  看过 34.5万  电池 150  ⋯ │
├──────────────────────────────────────────────────────────────┤
│ 00:12:04  弹 [舰5][🎖] 张三：前方的路很漫长                    │

│ 表情                                          [搜索表情____]   │
│ [通用][我的表情][本房间][大航海]   ← 分组 tab，一屏只画一组     │
```

| 项 | 规则 |
|---|---|
| 标签条 | 已打开房间的标签，按打开顺序排列，可横向滚动；激活标签高亮，连接状态点见 §3 |
| 多标签共存 | 已打开的房间保留各自的长连接与**会话缓冲**；切换标签只切换渲染，不断开、不清空 |
| 新增标签 | 在房间列表点击房间：已打开则激活该标签，未打开则新开 |
| 关闭标签 | 关闭该房间页，断开连接、销毁并清空该房间的会话缓冲；**不**删除房间数据（不调 `rooms_remove`） |
| 返回列表 | `xs` / `md` 下从房间页返回列表页，等同于关闭当前房间页 |
| 标签数量 | 不做硬上限；超过可视宽度横向滚动，不折叠为下拉 |
| 溢出标签 | 非激活标签不入渲染队列；连接与该房间的会话缓冲照常保持 |
| 稳定钩子 | 上述区域带 `data-testid`（`db-list-page` / `db-room-header` / `db-chat-scroll` / `db-bottom-anchor` / `db-msg-row` / `db-msg-list` / `db-msg-time` / `db-msg-avatar` / `db-msg-avatar-col` / `db-msg-identity` / `db-msg-badges` / `db-msg-name` / `db-msg-reply` / `db-msg-reply-name` / `db-msg-body` / `db-context-menu` / `db-panel` / `db-panel-close` / `db-emote-tabs` / `db-emote-tab` / `db-emote-group` / `db-emote-item` / `db-phrase-add` / `db-send-hint` / `db-composer-tools` / `db-account` / `db-gift-dock` / `db-follow-item` / `db-send-preview` / `db-owned-error` / `db-admin-panel` / `db-admin-confirm` / `db-admin-close` / `db-admin-error` / `db-admin-*-item`），冒烟脚本按它定位，不再依赖 CSS 类名。**行排版的几何断言只认这些钩子**：徽标组→昵称的间距量 `db-msg-badges` 与 `db-msg-name`，折行后的行盒量 `db-msg-body`（`Range.getClientRects()`），头像与首行的关系量 `db-msg-avatar-col` |

### 2.4 会话缓冲生命周期（契约 §4.3）

弹幕只在**内存环形缓冲**中保留，生命周期 = **一次房内会话**。

| 动作 | 会话缓冲 | 长连接 | 说明 |
|---|---|---|---|
| 进入房间（打开标签） | 新建，空，`local_id` 从 1 开始 | 建立 | 开始一次新会话 |
| 切换标签 | 保留 | 保持 | 不算离开房间 |
| 点击「刷新」（`rooms_reconnect`） | **保留**，不清空 | 重连 | 仍属同一次会话 |
| 返回列表页 / 关闭标签 | **销毁并清空** | 断开 | 会话结束 |
| 再次进入同一房间 | 全新会话，从空开始 | 新建 | 不复用上一次会话的缓冲 |

- 缓冲上限 5000 条（`history.buffer_rows`，契约 §8），超出丢最旧；进程退出即丢。
- 会话内允许向上回滚查看（`history_query`）；B 站无历史回放接口，本设计不做跨会话历史，也没有向前翻取更早内容的入口。

## 3. 房间头与连接状态

### 3.1 房间头

房间头固定在弹幕列表上方（不参与虚拟列表滚动）。头部只放「一眼要看的」信息，动作收进最右的 `⋯` 菜单：

| 元素 | 取值与来源 |
|---|---|
| 返回 | 回到房间列表页（等同关闭当前房间页） |
| 状态点 | 见 §3.3 |
| 标题 / 房间号 | 房间元信息（`follow_list` / `rooms_list` / `getRoomPlayInfo` 解析结果） |
| 连接状态文本 | 「已连接 / 连接中 / 已断开 / 异常」，`error` 时附退避详情（见 §3.3） |
| 观众数 | 在线人数（`ONLINE_RANK_COUNT` 的 `online_count`）与累计看过（`WATCHED_CHANGE` 的 `num`），两个都显示（用户 2026-09-12）；上游还没给过的一侧不显示，不用 `—` 或 `0` 顶替。人气值不再展示 |
| 电池 | `wallet_balance` 的数值（**只在房间头显示一处**，不在输入区重复占位） |
| `⋯` 菜单 | 房管面板 / 刷新连接 / 断开连接 / 显示·隐藏日志——都在右键菜单里（见 §3.2、§3.4、§3.5） |

会话时长不占头部（避免在窄窗口挤压标题）；`live_status` 只在房间列表页展示。

### 3.2 「刷新连接」（手动重连，`⋯` 菜单第一项）

用途：长连接卡住、推流暂时中断、或长时间无新消息时**手动重连**。命令为 `rooms_reconnect`（契约 §7）。

| 项 | 规则 |
|---|---|
| 位置 | 房间头最右 `⋯` 菜单的第一项，文案「刷新连接」 |
| 触发 | `invoke('rooms_reconnect', { roomId })` |
| 效果 | 立即断开并按退避序列重新建立连接；**保留**已收消息与滚动位置，不清空会话缓冲 |
| 状态反馈 | 触发后状态点立即变 `connecting`；成功转 `connected`，失败转 `error` 并继续退避 |
| 连续点击 | 处于 `connecting` 时菜单项禁用，避免并发重连 |
| 与自动重连的关系 | 手动触发会**清零退避计数**，即立刻重试而不是等下一个退避档 |
| 断线期间消息 | 重连成功后的消息继续追加到同一缓冲；断线期间的空档不回填 |

### 3.3 连接状态与按钮可用性

四种连接状态由 `danmubox://room` 与 `danmubox://status` 事件驱动：

| 状态 | 状态点视觉 | 房间头文本 | `⋯` 菜单的「刷新连接」 | 说明 |
|---|---|---|---|---|
| `connecting` | 黄色实心圆，1s 呼吸动画 | 「连接中…」 | **禁用** | 连接请求已发出、认证未完成 |
| `connected` | 绿色实心圆，不跳动 | 「已连接」 | **可用** | 长连接正常；卡住时用户手动刷新 |
| `disconnected` | 灰色空心圆 | 「已断开」 | **可用** | 未连接或已主动断开；点击立即重连 |
| `error` | 红色实心圆 | 「连接失败，第 N 次重试，Xs 后重试」 | **可用** | 认证失败或上游错误，正在退避重连 |

规则：

1. 退避序列按契约 §4 为 **5s / 10s / 20s / 40s / 60s 封顶**；倒计时数字每秒更新，显示为房间头横幅的一部分。
2. 认证被拒（`code != 0`）一律视为认证失败并按退避重连；**不得**在未知 code 上编造含义，横幅只显示原始 code。
3. 状态点同时出现在对应标签页上（同一套视觉），便于多标签下判断哪个房间需要刷新。

### 3.4 本人身份（`room_session`）

房管入口的权限前置要的是「我是这个房间的什么人」，这份身份单独有一条只读命令：

| 项 | 规则 |
|---|---|
| 命令 | `room_session(roomId)` → `RoomSession`（契约 §7）：`my_medal_level` / `my_medal_name` / `my_guard_level` / `is_admin` |
| 取数时机 | 进房间且会话就绪后读一次；引擎在会话建立时**并发**取一次并缓存，取到后另经 `danmubox://session` 事件推送（载荷是 `RoomSession`），界面据此更新，不轮询 |
| 无活跃会话 | 后端返回该房间的**全零身份而不报错**（与 `history_query` 同风格）。界面把「拿不到身份」当**无权限**处理，绝不先放行再等服务端报错 |
| 与登录态区分 | `danmubox://session` 这一个事件名上同时走登录态（`SessionState`，带 `logged_in`）与房内身份（带 `is_admin`）；界面按判别字段分派，**身份载荷不得覆盖登录态**（`ipc.md` 的事件表待补载荷判别说明） |
| 生命周期 | 会话级、不落盘；关标签 / 移除房间即丢弃（再进是全新会话，先清掉旧身份再读） |

## 4. 消息渲染

### 4.1 六种 `kind` 的视觉规范

`kind` 取值只有契约 §5 的六种。字号档基准见 §8.2，行高由内容折行实测（§7.1），不冻结固定值。

一行从左到右固定为 **`[时间戳列][头像][正文块：身份簇 ｜ 正文][合并计数]`**（用户 2026-09-12：重做每条弹幕的 DOM）。
行内**不再挂任何按钮**：行菜单只在**右键**上（用户 2026-09-12：「行尾 `⋯` 与右键菜单重复」，已删；房间头那个 `⋯` 是另一个元素，保留）。

**身份与正文是一个整体，头像是一列**（用户 2026-09-12：「头像、文本、身份、表情包互相之间很割裂」）。六条口径：

| 口径 | 规则 |
|---|---|
| 身份与正文共一条基线 | 身份簇（第 1 列）与正文（第 2 列）是**同一个网格的两列**，都从**首行盒顶**起算。共用一条基线来自「同一条**绝对**行高（`--row-line`）+ 同一个起点」，**不是** `align-items: baseline`：基线的取值是各自第一个行盒的基线，正文里一旦出现**块级大表情**（`.contentEmoteBulge`）那个行盒就不存在，基线会退化成「正文盒底边」，身份簇被拽到图片底边——这正是用户说的「发表情时显得错开」（改前实测：大表情那一行的昵称比头像低 **32px**） |
| 头像钉在首行盒上 | 头像列高度 = `--row-line`（行盒高）、钉在首行盒顶端（`align-items: flex-start`），头像在列里居中。不随折行掉到行的中间，也不被大表情顶下去。冒烟按 `rowIdentityOnFirstLineBox`（身份簇 / 头像 / 正文三者的顶边差 < 1.5px，两行表情弹幕都量）与 `layoutAvatarNotRowCentered`（反面对照）断言 |
| 间距只有两种 | 身份簇内部、头像↔正文块 = `--sp-1`（4px，"贴"）；身份簇↔正文 = `--sp-2`（8px，"分"）。行内出现第三种间距值即为 bug（§9.1） |
| 徽标属于人名 | 徽标组、昵称、回复标记装在同一个身份簇里（`data-testid="db-msg-identity"`），簇内 `--sp-1`、不留弹性空白；**徽标贴昵称，正文才与身份分开**。没有徽标时不渲染空徽标组（空盒会白吃一道间距） |
| 表情与文字同流 | 表情图放在正文块（`data-testid="db-msg-body"`）**里面**，与文字同一个行盒：尺寸 `--emote` = 1.1 × 行盒，上下各给一个负 `margin-block` 把超出行盒的那 10% 扣掉（图照画那么大，行盒与逐行间距不变）。`bulge_display` 的大表情（2 × `--emote`）是块级、独占一行。表情不另起一列、不与文字各站一个基线 |
| 多行正文悬挂缩进 | 正文块是网格的**第 2 列**，折行只发生在它内部，所以每一行的左边缘都等于首行的文字起点——不是回到头像下面。它**不需要**「块级左内边距 + 首行负 `text-indent`」那套：那套只有「身份与正文在同一个内联流里」才需要（同一内联流里两者共用一个左边缘，折行就会回到徽标下面）。由 `layoutHangIndentAligned` 两个视口断言 |
| 尺度同源 | 头像 / 徽标 / 表情图都从**一条基准**按固定比例派生（`--row-line` 行盒高）：头像与徽标 = 0.9 × 行盒，表情 = 1.1 × 行盒（§9.2）。基准用 `@property --row-line { syntax: "<length>" }` 注册——自定义属性默认在**使用处**按元素自己的字号解析，徽标（`--fs-1` = 0.79em）会把「0.9 行盒」算成 14.9px 而不是 18.9px，旧版三个尺度各自为政就是这么来的（用户 #3） |

| 单元格 | 规则 |
|---|---|
| 时间戳列 | `ui.show_timestamp` 打开时渲染（默认关闭）；`width: 8ch`（`--time-col`）+ `font-variant-numeric: tabular-nums` + 右对齐，**逐行纵向对齐**（用户 2026-09-12：时间要对齐）。宽窄屏都不隐藏 |
| 头像 | `Message.face`；空串不渲染，加载失败退化为昵称首字符占位（§4.2）。对齐口径见 §4.2：**垂直居中于首行** |
| 徽标组 | 见 §4.2，尺寸随字号缩放（em）。紧贴昵称（同一身份簇） |
| 昵称 | `--fg-dim`（低正文一档），**不吃**弹幕自身颜色：普通弹幕的颜色是 `16777215`（白），套到人名上在浅色主题里等于隐形（用户 2026-09-12 实测「用户名是白色、看不见」）。超长时 14em 截断（窄屏下不许把正文挤出屏幕） |
| 回复标记 | `reply_to_uid != 0`（契约 §5）时在昵称之后、正文之前显示「回复 @昵称」（`data-testid="db-msg-reply"`，弱化小标、定宽截断 14em、完整名字在 `title`）；非回复（`reply_to_uid == 0` 或 `reply_to_uname` 为空串）不渲染这一格。它**不占正文列**，因此不妨碍正文折行与时间戳/昵称的纵向对齐。被 @ 的名字单独一格（`db-msg-reply-name`）：上游给了 `reply_uname_color`（实测 `#FB7299`）就上色，空串沿用标记自身的弱化色（**空串不是颜色**，与粉丝牌真彩色同一口径）。这一格也是「纯 @ 某人」的槽位——收包侧区分不出 @ 与回复（引擎 2026-09-12 实测：`extra` 45 个键里没有任何指回被回复弹幕的 id，`reply_type_enum` 与 `reply_mid != 0` 同构、`show_reply` 恒为 `true`），因此两种形态共用这一格、只差文案，不各开一列 |
| 正文 | 折行；**弹幕自身颜色只落在这里**（`Message.color` → `#RRGGBB`；`0` 与 `0xFFFFFF` 都按「未指定」处理 → 主题前景色，见 §4.3）；超过 4 行截断并给「展开」 |
| 合并计数 | `count > 1` 或 `kind == gift` 时在正文**行内**末尾渲染 `×N`：跟在最后一行文字后面，不另占一行、不另开一栏 |

| kind | 颜色（本地设计 token） | 图标位 | 对齐 | 字号档 | 备注 |
|---|---|---|---|---|---|
| `danmaku` | **正文**取消息 `color`（十进制 RGB → `#RRGGBB`）；`0` 与 `0xFFFFFF` 视为未指定 → 主题前景色；昵称 / 时间戳 / 徽标都不吃它 | `弹` | 左对齐 | 正文档 / 昵称低一档 / 时间最低档 | 竖条贴行首，仅此一种取消息颜色 |
| `gift` | 竖条 `--gold #C08A2E`；礼物名加粗；`amount` 用金额色 | `礼` | 左对齐 | 正文档 / 昵称低一档 | 金额单位见 §6.4、§13 |
| `superchat` | 卡片，背景与边框取自 SC 档位 token `--sc-1 … --sc-5`（档位边界见 §13）；金额行加粗 | `SC` | 左对齐，卡片占满行宽 | 金额低一档加粗 / 正文档 / 昵称低一档 | 高度随内容行数增长 |
| `interact` | 竖条 `--neutral #6B7280`；正文 `--fg-muted` | `入` | 左对齐 | 最低档 | 弱化显示；默认显示一会儿后自动消失，见 §4.8 |
| `guard` | 竖条按 `guard_level`：1 总督 `--guard-1 #C0392B` / 2 提督 `--guard-2 #8E44AD` / 3 舰长 `--guard-3 #2980B9`；`0` 用中性色 | `舰` | 左对齐 | 正文档加粗 / 昵称低一档 | 文案见 §13 |
| `system` | 无竖条；文本 `--fg-subtle` | `系`（居中时可省略） | 整行居中 | 最低档 | 由 `core` 归一化后的系统事件；**默认不渲染**，开关见 §4.8 |

色值为本项目本地设计 token，与 B 站网页端配色的差异见 §13。

表情弹幕（`Message.emote` 非空）**画图不画字**：此时正文就是表情名，只显示文字会被当成「表情没渲染」。图与文字同高对齐，`alt` 与 `title` 都填表情名——图加载不出来时浏览器回退显示 alt，不至于变成空白。

表情尺寸**不用固定像素、全部用 em**，因此跟着 `ui.font_scale` 一起缩放（用户 2026-09-12：字号要同步调整表情尺寸）：

| 位置 | 尺寸 | 说明 |
|---|---|---|
| 弹幕正文里的表情 | `--emote` = `1.1 × --row-line` | 以**行盒高**为基准；`ui.font_scale = 1`（正文 14px、行盒 21px）时 = 23.1px。超出行盒的 10% 由负 `margin-block` 从行盒里扣掉，所以一行表情不会把行高撑得忽高忽低 |
| `bulge_display = true`（大表情） | `2 × --emote` + 4px 圆角 | 官方把这类表情画两倍大，见官方 `emoticon.bulge img { height: 40px }` |
| 表情面板里的缩略图 | 通用 `1.5em`；**非通用（本房间 / 粉丝牌 / 大航海）`2.2em`** | 非通用那几族本来是大图，缩成通用那么大看不清（用户 2026-09-12） |

**一切来自上游 CDN 的图片都必须在无 Referer 的前提下请求**（`index.html` 的 `<meta name="referrer" content="no-referrer">`）：该 CDN 有防盗链，非 bilibili 来源返回 403，浏览器再以 ORB 拦掉，表现为整屏问号且控制台毫无线索。

### 4.2 身份徽标与头像

徽标只从契约 §5 的既有字段派生，**不新增字段**：

| 徽标 | 派生条件 | 视觉 | 优先级 |
|---|---|---|---|
| 主播 | `uid == Room.anchor_uid`（由房间解析得到的 `uid`，**不是** `Message` 字段） | 红底渐变胶囊，白字「主播」 | 1（职衔槽最高） |
| 房管 | `Message.is_admin == true` | 蓝底渐变胶囊，白字「房管」 | 2 |
| 总督 | `guard_level == 1` | `--guard-1` 渐变胶囊「总督」 | 3（大航海槽最高） |
| 提督 | `guard_level == 2` | `--guard-2` 渐变胶囊「提督」 | 4 |
| 舰长 | `guard_level == 3` | `--guard-3` 渐变胶囊「舰长」 | 5 |

**两个槽位 + 并列规则**：

| 槽位 | 容纳 | 互斥规则 |
|---|---|---|
| 职衔槽（昵称左侧第一槽） | 主播、房管 | 二者互斥，**主播优先**：`uid == anchor_uid` 为真时即使 `is_admin` 也为真，只渲染主播徽标 |
| 大航海槽（职衔槽右侧） | 总督、提督、舰长 | `guard_level` 是单值，天然至多一枚 |

- 两个槽位**可并列**：如「房管 + 舰长」同时渲染；「主播 + 总督」也允许（上游字段允许时）。
- 主播与房管不得同时出现（同一人）；`uid == anchor_uid` 时忽略 `is_admin`。
- 徽标顺序固定为 `[职衔槽][大航海槽][粉丝牌]`，昵称紧随其后；徽标是**昵称前置**元素，不占用行首竖条。
- 徽标组、昵称、回复标记属于**同一个身份簇**（`data-testid="db-msg-identity"`，簇内间距 `--sp-1`）：身份是「谁在说话」的一部分，不是与昵称并列的一栏（§4.1）。
- **大航海槽只认 `Message.guard_level`（本房间的大航海等级）**：粉丝牌上的 `medal_guard_level` 是**牌子所属房间**的身份，只用于牌面样式，**不得**拿它兜底画舰长标——否则「戴着别的房间舰长牌的人」在本房间也会亮出舰长标（用户 2026-09-12 反馈 #12，契约 §5 已把两者分层）。

**形状照官方聊天栏量得的值**（2026-09-12 取官方直播间前端产物）：

| 项 | 官方 | 本界面 |
|---|---|---|
| 徽标形状 | 胶囊：`border-radius: 8px`、`height: 15px`、`padding: 2px 6px 2px 2px`、12px 白字 | 同形，但尺寸用 em（`height: 1.35em` / `font-size: 0.79em` / `border-radius: 0.55em`）随 `ui.font_scale` 缩放 |
| 描边 | `1px solid var(--borderColor)`（牌面同色系） | 粉丝牌有 `medal_color_border` 时用它，否则 `1px solid color-mix(in srgb, #fff 45%, transparent)` |
| 底色 | `linear-gradient(45deg, v2_medal_color_start, v2_medal_color_end)` | 主播 / 房管 / 大航海用本地 token 的同款 45° 渐变；粉丝牌见下 |
| 等级格 | 右侧独立一格、宽度固定（1 位 `4px` / 3 位 `15px`），白字 | 右侧独立一格（`tabular-nums`，深色半透明底） |

**粉丝牌配色**：契约 §5 转发了上游四件套 `Message.medal_color_start` / `_end` / `_border` / `_text`（`user.medal.v2_medal_color_*`，带 alpha 的 CSS 十六进制串，如 `#3FB4F699` / `#FFFFFF`），界面**优先用真彩色**：`start` / `end` 作 45° 渐变两端，`border` 作描边色，`text` 作牌面文字色。

| 情况 | 渲染 |
|---|---|
| `medal_color_start` 与 `_end` 都非空 | 用上游真彩色做渐变 |
| 任一为空串 | 退回**按牌名派生的稳定色相**（同一主播每次一致、不同主播不同色）——这是本地兜底，不是上游值 |
| `medal_color_border` / `_text` 为空串 | 各自退回 CSS 默认（半透明白描边、白字），不拿黑色顶替 |

**空串不是颜色**（引擎保证缺失即空串）：不得把空串当 `#000000` 渲染，也不得用它拼 `linear-gradient` 的色标。

`medal_guard_level`（牌子**所属房间**的舰长标记，契约 §5）留给牌面样式。本界面**暂时不用**它做视觉区分：官方对它的具体画法目前没有实测依据（§13 的口径是不编造未实测的上游行为），而现有牌面（真彩色 + 等级格）已够辨识；等官方产物核实后再定，`docs/contract.md` §5 与 `protocol.md` A39 已写明它不得用于本房间的舰长标。

**头像**（需求 §2.6，`Message.face`）：

| 情况 | 渲染 |
|---|---|
| `face` 非空 | 圆形缩略图（`--avatar` = `0.9 × --row-line`，随字号缩放），`alt=""`、`title=昵称`（装饰性图片，昵称已在旁边） |
| `face` 为空串 | **不画图**（上游没给就没有头像），但**头像列照常占位**（同样 `--avatar` 宽的空列，`data-testid="db-msg-avatar-col"`）：否则这一行的身份簇 / 正文会整体左移，与其它行对不齐（用户 2026-09-12：时间与列要对齐） |
| 加载失败 | 退化成昵称首字符的圆形占位（居中大写，底色 `--bg-input`） |

**头像的对齐口径：钉在首行盒上、在其中居中**（用户 2026-09-12 要求的「选一种、站一致」——这里选定的是首行居中，不是整行居中）。做法：头像列高度取行盒高（`--row-line`），在行容器里顶对齐，头像在列里居中（§4.1）。因此正文折成三行时，头像仍与**第一行**齐平，不会被拽到行的中间；正文里出现大表情时也不会被顶下去（改前：昵称比头像低 32px）。冒烟按 `layoutAvatarFirstLineDelta`（头像中心 − 首行行盒中心）、`rowIdentityOnFirstLineBox`（身份簇 / 头像 / 正文三者顶边一致）与 `layoutAvatarNotRowCentered`（反面对照）两个视口都断言。

> 口径说明：居中于**行盒**而不是居中于**字形墨迹**。人名 13px、正文 14px，两者同一条基线但墨迹中心本来就差 ~2.2px，选哪个都会偏另一个；行盒是这一行的结构尺寸（也是 `--row-line` 这条基准），拿它当锚更稳、也更好解释。

- 占位列的宽度是 `--avatar`，与有头像时一致；占位元素不带 `db-msg-avatar`，因此「没头像」与「头像加载失败」在 DOM 上仍可区分。
- 点击昵称（含徽标区域）在系统浏览器打开该用户主页；`uid == 0`（游客/未知）时昵称不可点击。

### 4.4 本地发送回显与被吞标记

本地发送的弹幕按 `SendOutcome`（契约 §5）决定回显，避免与上游回推重复：

| `SendOutcome` | 是否本地回显 | 行内标记 |
|---|---|---|
| `ok` | **不**回显（等上游通过 `danmubox://message` 回推，避免重复） | 无 |
| `blocked_platform` | 回显一条 `danmaku` 行 | 整行**红色**删除线 + 行尾红色角标「平台未展示」 |
| `blocked_room` | 回显一条 `danmaku` 行 | 整行**黄色**删除线 + 行尾黄色角标「直播间未展示」 |
| `rate_limited` / `medal_required` / `muted` / `failed` | **不**回显（消息未发出） | 提示文案见 §6.5，草稿按 §6.1 保留 |

被吞标记规则（参考社区脚本「Bilibili Live Banned Danmaku Marker」的判定思路，判定来源见 `protocol.md`）：

| 判定 | 判定值 | 竖条 | 文本 | 角标 | 悬浮说明 |
|---|---|---|---|---|---|
| 平台吞（风控） | 上游 `msg` / `message` == `"f"` | 红色 `--block-platform #D93025` | 删除线 + 弱化 | 「平台未展示」 | 「该弹幕未出现在公开弹幕流（平台侧处置）；内容已回显在响应 `data.mode_info.extra`」 |
| 直播间吞（主播/房管） | 上游 `msg` / `message` == `"k"` | 黄色 `--block-room #F0A020` | 删除线 + 弱化 | 「直播间未展示」 | 「该弹幕被本直播间处置（主播或房管）」 |
| 其他失败 | 其余 code | 不产生行 | — | — | 走 §6.5 文案表 |

- 只有本人发送的弹幕才带被吞标记；他人消息不产生该标记。
- 标记为会话内状态，不落盘；离开房间即消失。

表情选择器的内容 = **接口给的包** ＋ **从收到的弹幕里学到的表情**（按 `emoticon_unique` 去重，接口优先）。
「接口给的包」是**两路合起来**的一侧：`emotes_list` 的按房间包（通用 / 本房间 / 粉丝牌 / 大航海）
与 `emotes_owned` 的主站「我的表情」；学到的那些只补这两路都没给的唯一键。后者的必要性：
上游有些表情家族（`upower_` 的 UP 主专属表情）不在直播表情接口里，收下来却选不到、就发不回去（`protocol.md` A35）。

「我的表情」并进接口侧这件事不只是分组好看：输入区的**发送预览**只认这一份合并结果，
若它加载太晚，草稿里的 `[表情名]` 会**静默地**显示成纯文字（预览失效）。因此加载时机固定为
「进房间且会话就绪后拉一次」，失败不阻塞输入框，只在面板里给原因与重试（§6.3）。

### 4.5 行右键菜单

行内不再挂一排动作按钮（用户 2026-09-12：「很多可以放到右键的逻辑尽量放到右键菜单里」）。

菜单是 `position: fixed` 的浮层，弹出时把坐标收敛进视口；点别处、按 Esc、窗口尺寸变化都会关掉它。
菜单根节点带 `data-testid="db-context-menu"`，冒烟脚本按它断言。

进入房间时，服务端会先铺一批「最近的弹幕」（上游 `data.room`，上限 10 条，**不可翻页**，见 `protocol.md` 附录 A30；语义见 `contract.md` §4.3）。

| 项 | 规则 |

### 4.8 互动消息自动消失与系统通知

两个开关都来自契约 §8，属于「消息是否出现、出现多久」，与关键字过滤相互独立（求值顺序见 §8.1）。

| 开关 | 偏好键 | 默认 | 行为 |
|---|---|---|---|
| 互动/进场消息自动消失 | `ui.interact_auto_hide` | `true` | `interact` 行显示 8 秒后淡出并从列表移除；关掉则常驻（官方客户端即「显示一下就消失」） |
| 系统通知 | `ui.system_notice` | `false` | 关闭时 `system` 行不渲染；打开后与普通行同样式渲染 |

- 自动消失的实现：行按 8 秒跑一段淡出动画，到点由 store 把该条从列表里摘掉，空间随之回收；同一常量（`types.ts` 的 `INTERACT_AUTO_HIDE_MS`）同时驱动动画与摘除，两者不会错位。
- 「系统通知」包含开播 / 下播 / 标题变更 / 公告（`core` 的 `SYSTEM_CMDS` 全集）：**不区分公告类与生命周期类**，一个开关管全部——用户要的是「别默认刷屏」，拆成两个开关只会多一层配置。
- 两个开关都只影响渲染，不改变会话缓冲：关掉再打开，本会话已收到的消息会重新出现。

已添加房间多于一个时，界面顶部显示标签页（需求 §2.8）：点一下切到该房间，标签上带连接状态圆点。

### 4.9 房管：禁言 / 黑名单 / 屏蔽词（issue #3）

房管能力分两个入口：**行右键菜单**（对某个具体的人）与**房管面板**（名单与屏蔽词的增删查）。权限前置统一取自 `RoomSession.is_admin`（IPC `room_session`，契约 §7）：**拿不到身份 = 按无权限渲染**，绝不先放行再等服务端报错。

| 入口 | 位置 | 内容 |
|---|---|---|
| 对某个人的操作 | 行右键菜单（§4.5） | 「禁言…」「拉黑」「解除禁言」三项；非房管置灰并给出原因 |
| 房管面板 | 房间头 `⋯` 菜单 →「房管面板」 | 三块：禁言名单、黑名单、屏蔽词；列表 + 增删 |

**房管面板**（`data-testid="db-admin-panel"`）与输入区的弹出面板同处文档流（输入区上方、向上展开），展开时只挤压弹幕列表，不遮挡最新弹幕。

| 块 | 列表来源 | 增 | 删 |
|---|---|---|---|
| 禁言名单 | `admin_silent_list`（`SilentUser[]`） | uid 输入 + 「禁言」（时长在确认条上选） | 每项「解除禁言」 |
| 黑名单 | `admin_blacklist_list`（`BlacklistedUser[]`） | uid 输入 + 「拉黑」 | 每项「移出黑名单」 |
| 屏蔽词 | `admin_keywords_list`（`string[]`） | 文本输入 + 「添加屏蔽词」（回车同效） | 每项「删除」 |

- **无权限也允许打开面板**：只读列表照常请求，上游的拒绝原样展示为 `code` + `message`（不翻译、不猜语义），三块的错误各自独立显示、不互相清空。
- 面板打开时刷新一次三块列表与身份；写操作成功后自动重读三块（以远端为准，不在本地猜上游怎么变）。
- 纯文本的输入沿用输入区已有的组件风格（input + 按钮，回车提交）。

**二次确认（硬要求）**：所有写操作——禁言、解除禁言、拉黑、移出黑名单、**添加与删除屏蔽词**——都先出确认条（`data-testid="db-admin-confirm"`），文案必须说清**对象与时长**，例如：

| 动作 | 确认文案 |
|---|---|
| 禁言 | `禁言 张三（uid 1234）· 时长：本场直播`，旁边的下拉可改成本场直播 / 永久 / 1 / 6 / 24 小时 |
| 解除禁言 | `解除 张三（uid 1234） 的禁言` |
| 拉黑 | `拉黑 张三（uid 1234）（会解除关系并禁止互动，比禁言重）` |
| 移出黑名单 | `把 张三（uid 1234） 移出黑名单` |
| 加 / 删屏蔽词 | `添加屏蔽词「刷屏」` / `删除屏蔽词「刷屏」` |

- 时长取值就是 `admin_mute` 的 `hour`（契约 §7）：`0` 本场直播 / `-1` 永久 / 其余为小时数；界面只提供这五档，不手输。
- 只从面板的 uid 输入框发起时没有昵称，确认文案写 `uid 1234`（不编造昵称）。
- 写操作进行中按钮禁用（避免并发重复提交）；失败时确认条保留、原因进错误条（原样 `code` + `message`），成功则收起并给出提示。

## 5. 礼物栏双模式（`ui.gift_panel_mode`）

`ui.gift_panel_mode`（契约 §8）取值 `merged` / `separate`，默认 `merged`。

| 模式 | 含义 | `gift` / `guard` 的渲染位置 |
|---|---|---|
| `merged` | 礼物**混在弹幕栏** | 直接作为 `gift` / `guard` 行插入聊天流，按 §4.1 渲染 |
| `separate` | **输入区下方的独立礼物栏** | 聊天流不再渲染 `gift` / `guard`；两类消息改在礼物栏渲染，**每页全宽、可折叠**（`merged` 时该栏不存在） |

两种模式都受 `filter.kinds` 白名单支配：白名单移除 `gift`（或 `guard`）时，**两处都不渲染**。

## 6. 输入区

### 6.1 布局与草稿

输入区自上而下：弹出面板（若打开，见 §6.3）→ 引用条（有回复上下文时出现，带「取消」）→ 「将发送」预览（草稿里有表情时）→ 文本输入框 → 工具行（左：表情 / 短语 / 筛选 三个面板入口；右：发送）→ 发送结果行（**只在需要用户做点什么时**才渲染，见 §6.5）。

| 项 | 规则 |
|---|---|
| 文本框 | `<textarea>`，自适应 1–5 行，超出内部滚动；`Enter` 发送、`Shift + Enter` 换行为默认行为，不可配置 |
| 工具行 | 三个面板入口互斥（同时只开一个），点第二次关闭；按钮 `mousedown` 不抢焦点，因此打开面板时光标与草稿都留在输入框里 |
| 插入位置 | 表情 / 短语一律插到**光标处**（插完把光标移到插入内容之后），不再固定追加到末尾 |
| 发送按钮 | 有明确文本「发送」，不用纯图标；发送中显示节流倒计时（本地最小间隔 2s，契约 §4） |
| 草稿保留 | 每个房间的草稿按 `room_id` 存在前端 store，**会话内**保留（切换标签不丢、返回列表则随会话销毁）；**不写入** `prefs.json`（契约 §8 无对应键） |
| 发送后 | `ok` 时清空文本框；失败时按 §6.5 **保留草稿**并把失败原因显示在输入区上方 |
| 长度提示 | 超过上游长度上限时，发送按钮禁用并显示计数；上限值见 §13 |

### 6.2 短语与 @

| 功能 | 规则 |
|---|---|
| 内置快捷短语 | 编译期常量表（常用语 + 颜文字），不占偏好键；点选插入光标处 |
| 自定义短语 | 用户新增 / 改名 / 删除，存 `composer.phrases`（字符串数组）。**新增**用面板里**独立的一行**（面板头下方固定行：输入框占满除「添加」按钮外的整行，回车或「添加」都提交，`data-testid="db-phrase-add"`）；**改名与删除**在短语上**右键**，菜单两项「编辑 / 删除」，编辑是就地变成输入框（Enter 提交、Esc 取消） |
| 加一条那一行不许被顶走 | 短语面板自上而下固定为「面板头 → **加一条（固定行）** → 芯片区（`overflow-y: auto`）」：芯片再多也只让**芯片区**滚动，加一条那一行永远在场（用户 2026-09-12：竖屏下加短语时输入框被挤占）。冒烟按 `phraseAddRowInsidePanel`（在面板内）、`phraseAddRowStaysPut`（相对面板顶的偏移不变）、`phraseAddRowWideEnough`（≥ 120px）与 `phraseChatInputStillVisible`（聊天输入框仍完整落在视口里、被面板顶到下面而不是被盖住）断言 |
| 重复与空值 | 添加或改名撞上已有短语、或内容为空时**给出提示**（「这条短语已经有了」/「短语不能为空」），不静默丢弃 |
| 颜文字 | 归入内置快捷短语分组，面板里独立一行，不占偏好键 |
| @某人 | 行菜单「＠TA」把 `@昵称 ` 插到**光标处**；上游是否支持 at 语法与 at 后是否真正提醒见 §13，UI 不保证提醒效果 |
| 回复 | 行菜单「回复」后在输入区上方显示引用条（昵称 + 内容摘要）；发送时按上游支持的 at 语法拼装文本（`Message` 无引用字段，本地不渲染引用结构）；取消引用则清空引用条，草稿文本不变 |

**@ 目标与文本同源（用户 2026-09-12：「@某人 后文本框内会有 @xxx 但是删掉这个后发的弹幕还是会 @」）**：

| 项 | 规则 |
|---|---|
| 目标来源 | **发送时从草稿文本派生**，不另存一份「目标状态」——两者因此不可能不一致 |
| 带上目标的条件 | 草稿里仍有 `@昵称 `（插入时补的那个空格还在）或草稿以 `@昵称` 收尾；只有前缀相同（如 `@昵称甲乙`）不算 |
| 取消方式 | 把文本里的 `@昵称` 删掉即可，不需要额外的「取消 @」按钮 |
| 可见提示 | 条件成立时在输入区上方显示「将 @昵称 · 删掉文本里的 @昵称 即取消」（`data-testid="db-mention-hint"`）；它是派生出来的，显示的与发出去的永远一致 |
| 与回复的区别 | 「回复」是**显式**的引用条（`db-reply-bar`，可见、带「取消回复」），不依赖文本，因此照旧带 `replay_dmid`；两条路径同时存在时**回复优先** |

> 旧实现的两个毛病（用户 2026-09-12「短语的增删界面逻辑修正一下」）已改掉：
> ① 删除按钮删的永远是「列表里最后一条」，无法对应到具体哪一条；
> ② 短语的 `title` 写着「右键删除」但根本没有右键处理，撞名时还会静默清空输入框。

### 6.3 表情面板（`emotes_list` + `emotes_owned`）

按**当前房间身份**加载（`RoomSession`，契约 §5）：`my_medal_level` / `my_medal_name` / `my_guard_level` / `is_admin`。面板结构：搜索框 → **分组 tab**（`data-testid="db-emote-tabs"` / 每个 tab 一个 `db-emote-tab`）→ 当前 tab 的**表情网格**（`db-emote-group`，格子里一个 `db-emote-item`）。

**一屏只画一组**（用户 2026-09-12：「表情面板改成 tab」）：分组不再纵向堆在同一个滚动区里，点 tab 切组、切组回到格子顶部。搜索是在**所有组**里搜的，tab 因此只列「当前有命中的组」，选中的那组被搜索过滤空时自动回落到第一组（派生值，不留在 state 里）。

| 分组（`package_kind`） | 说明 |
|---|---|
| 通用 `common` | 全站通用表情（实测 `pkg_type = 1`） |
| 我的表情 `owned` | 主站「我的表情」（`emotes_owned`，`upower_` 家族）：不在直播表情接口里，只能从这里取；`room_id = 0` |
| 本房间 `room` | 房间专属表情（实测 `pkg_type = 2` 且表情无解锁门槛）+ 从弹幕学到的表情 |
| 粉丝牌 `medal` | 我在**该直播间**的粉丝牌档位表情（实测：包内 `unlock_need_level > 0` / `identity ∈ 1..4` 即归此组，与包名无关） |
| 大航海 `guard` | 按当前大航海等级可用集合 |

**分组归属与「当前身份能不能用」都由接口侧判定**，界面不自己算：拿到的 `package_kind` 出 tab，拿到 `Emote.locked` 就置灰。上游**不按权限过滤**（引擎 2026-09-12 实测：两个身份不同的账号对同一房间各拉一次，3 包 / 68 个完全相同、连顺序都一样，只有舰长专属那批的 `perm` 随身份 0↔1），所以「无权限」在界面上是**置灰列出来**，不是消失（用户 2026-09-12：「置灰显示，不是隐藏」）。

**分组顺序固定为** 通用 → 我的表情 → 本房间 → 粉丝牌 → 大航海（接口给的包在前，学到的表情归「本房间」）。

| 项 | 规则 |
|---|---|
| 打开 | 工具行「表情」按钮；再点关闭；打开时保持输入框焦点与草稿（面板在输入框**上方**向上展开） |
| 加载时机 | ①进房间且会话就绪后拉一次 `emotes_owned`（与房间无关，成功一次即不再请求）；②面板打开时若**上次失败**再试一次，并在面板里给「我的表情加载失败：<原样 code + message>」+「重试」。**失败绝不阻塞输入框**，已加载的分组照常可用。`locked` 是**按调用者身份当场算**的（同一房间换账号会变），所以换房间 / 换账号后要重新拉一次 `emotes_list`，否则会沿用旧身份算出来的灰 |
| 分组 tab | 列出接口给了的组（顺序固定：通用 → 我的表情 → 本房间 → 粉丝牌 → 大航海），tab 上带该组的条数；身份变化（进不同房间）时重建并回到「通用」 |
| 网格 | 等宽格子 `repeat(auto-fill, minmax(3em, 1fr))`，一行放几个由面板宽度定；格子里的图居中。**表情格是面板里唯一会滚的部分**（面板头与分组 tab 常驻）——tab 是切组的唯一入口，被格子滚走就得先滚回顶部；面板自身限高（`max-height: 260px` / 窄屏 45vh）只由格子承担。长列表虚拟化或分页加载。冒烟按 `panelScrollsInternally`（格子在自己滚）与 `panelTabsStayVisible`（把格子滚到底，tab 位置不动）断言 |
| 无权限的表情 | `Emote.locked == true` 的格子**照常列出**但置灰：`filter: grayscale(1)` + `opacity: .45`——灰的是颜色不是尺寸，仍能认出是哪一个；**不隐藏、不禁用**（`title` 说明「当前身份用不了，置灰只是提示，发送仍由上游判定」，点了照样插进草稿）。**字段缺失（老后端）= 可用**，不许整面板变灰（契约 §5：置灰是提示，真正的闸门在上游发送侧）。冒烟按 `panelLockedEmoteListed` / `panelLockedEmoteDimmed` / `panelLockedEmoteSameSize` / `panelLockedEmoteSelectable` / `panelMissingLockedTreatedAsUsable` 断言 |
| 搜索 | 面板顶部搜索框，按 `Emote.text` 做 Unicode 大小写折叠的子串匹配；无结果时显示「没有匹配的表情」 |
| 尺寸 | 通用 `1.5em`、**非通用（我的表情 / 本房间 / 粉丝牌 / 大航海）`2.2em`**，全部相对面板字号（= 正文基准 × `ui.font_scale`），因此字号一改表情跟着变（用户 2026-09-12） |
| 插入 | 点击表情把 `Emote.text` 插到光标处（**仅用于显示**）；面板**不自动关闭**，支持连续插入 |
| 发送 | 草稿与点选的表情一致时，按**表情弹幕**发送：`chat_send` 带 `emote.emoticon_unique`，上游最终收到的 `msg` 就是它（适配器映射，见 `protocol.md` §11.4）；草稿一旦被手工编辑就退回普通文本。必须记住「点的是哪一个」——表情名会重名（实测「贴贴」同时在通用包与房间包里） |
| 预览 | 草稿里能对上表情名的片段换成图片（§6.1 的「将发送」）；对得上才显示，是「表情名会被当成文字发出去」的可见防线 |
| 图片 | 单元格按 `Emote.url` 展示缩略图；图片加载失败时回退显示 `Emote.text` 文本；不因图片失败阻断插入 |
| 房间专属 | `Emote.room_id != 0` 的表情只在对应房间展示（`room_id` 与当前房间一致）；「我的表情」`room_id = 0`，任何房间都可见 |
| `key` | 仅用于列表 key 与去重，不展示 |
| 空态 | 分组返回空列表时显示「该分组暂无可用表情」 |

### 6.5 发送结果与失败文案

`chat_send` 返回 `SendOutcome`（契约 §5，七个取值）。发送到结果返回前的等待期，发送按钮显示节流倒计时并禁用。

| `SendOutcome` | 含义 | UI 文案 | 位置 | 草稿 | 回显 |
|---|---|---|---|---|---|
| `ok` | 已发出并进入公开弹幕流 | 无（静默） | — | 清空 | 不本地回显，等上游回推 |
| `blocked_platform` | 被平台风控吞掉 | 「已发送，但未出现在公开弹幕流（平台侧处置）」 | 输入区上方横幅 + 行内标记（§4.4） | 清空 | 红色删除线回显 |
| `blocked_room` | 被直播间吞掉 | 「已发送，但被本直播间处置（主播或房管）」 | 输入区上方横幅 + 行内标记（§4.4） | 清空 | 黄色删除线回显 |
| `rate_limited` | 频率限制 | 「发送过于频繁，请稍后再试」+ 倒计时（本地最小间隔 2s，契约 §4） | 输入区上方横幅 | **保留** | 不回显 |
| `medal_required` | 粉丝牌等级不足 | 「本直播间需粉丝牌等级达标才能发言」 | 输入区上方横幅 | **保留** | 不回显 |
| `muted` | 已被禁言 | 「你已被禁言（全局或本直播间）」 | 输入区上方横幅 | **保留** | 不回显 |
| `failed` | 其他失败 | 「发送失败」+ 原始 code 与 message | 输入区上方横幅 + 「重试」按钮 | **保留** | 不回显 |

规则：

0. **成功的发送不额外提示**：弹幕已经出现在列表里，输入区上方那行「上次发送：已发出」已按用户 2026-09-12 删除（原话：没意义且不协调）。那一行只在下面这些情况渲染：未登录、或 `SendOutcome != ok`；没有话要说时**整行不渲染**（不留空白行，窄屏也不白占 20px）。冒烟按 `sendHintAbsentOnSuccess` 断言。
1. 文案**不猜测**上游细节；`failed` 必须展示上游原始 code 与 message，不改写语义。
   上游原话与 code 由 `chat_send` 返回的 `detail` 字段携带（契约 §5 `SendReport`），
   界面直接拼接显示，例如「发送失败 · 发送失败，请先移除该用户黑名单（code 10023）」。
2. 除 `ok` / `blocked_*` 外一律保留草稿，用户可直接重试。
3. 横幅自动消失时间为 5s（`failed` / `muted` 常驻直到用户操作或修改草稿），用户可手动关闭。
4. 被吞判定（`"f"` / `"k"`）由适配器归一化，UI 只消费 `SendOutcome`，不做字符串判定。
5. 游客未登录时发送按钮禁用，`title`「需登录后发送」。

## 7. 虚拟列表、自动滚动与暂停

### 7.1 虚拟列表

使用 TanStack Virtual 的元素级 `useVirtualizer`，滚动容器是聊天流自身的 `<div>`（不是 `window`），保证桌面与 Android WebView 的滚动/惯性一致，并允许房间头与输入区独立于滚动。

| 参数 | 取值 | 说明 |
|---|---|---|
| `count` | 过滤与合并后的可见行数 | — |
| `getScrollElement` | 聊天流容器 ref | 元素级虚拟化 |
| `estimateSize` | 按 `kind` 基准行高 × `ui.font_scale` 估算 | 实际高度由 `measureElement` 写回 |
| `getItemKey` | `local_id`；合并行取行内首条消息的 `local_id` | 契约 §5：`local_id` 仅用于 UI key 与本地引用 |
| `overscan` | 12（窄屏 8） | 真机不达标时按 §13 下调 |
| `measureElement` | 开启 | 动态行高实测写回 |
| `scrollToFn` | 自定义 | 跟随模式瞬时定位（§7.3） |
| `lanes` | 1 | 单列 |

行高与动态处理：

| 场景 | 处理 |
|---|---|
| 内容折行 | 按容器宽度折行；超过 4 显示行时截断，行尾给「展开」，展开状态为行本地 state，不写入 store |
| 长昵称 | 昵称截断到 8 字符 + `…`；完整昵称放 `title` |
| 粉丝牌 | 最多 6 字符，超出截断；等级数字最多 3 位 |
| `rowScale` | 即 `ui.font_scale` 当前值（§8.2） |
| 图片 / 表情 | 消息正文不加载远程图片（表情图片只在表情面板按需加载，见 §6.3） |
| `ResizeObserver` | 容器宽度变化（抽屉开合、窗口缩放）触发重新测量，并在同一帧内恢复锚点 |
| 字体 | 只用系统字体栈，避免字体加载完成后行高跳变 |

### 7.2 自动滚动与暂停

| 状态 | 进入条件 | 行为 | 退出条件 |
|---|---|---|---|
| 跟随最新 `following` | 进入房间且 `ui.auto_scroll = true`；点击「回到最新」；滚动到距底 ≤ 8px | 每次 flush 后定位到列表底部；隐藏「回到最新」 | 距底 > 8px |
| 用户暂停 `paused` | 上滑 / 拖动滚动条使距底 > 8px | 冻结视口位置；新消息不改动 `scrollTop`；显示「N 条新消息 · 回到最新」 | 点击「回到最新」；滚回距底 ≤ 8px |
| 悬停暂停 `hovered` | `ui.pause_on_hover = true` 且鼠标进入聊天流区域 | 与 `paused` 相同的冻结行为，但不显示「回到最新」 | 鼠标离开后回到进入前的状态；触控设备不进入该状态 |
| 非激活标签 `background` | 该房间不是当前标签 | 不入渲染队列；连接保持、会话缓冲照常追加 | 切回该标签 |

规则：

1. 距底阈值 8px 是唯一判定依据，不用滚动方向启发式（手势惯性下会抖动）。
2. 初始状态由 `ui.auto_scroll` 决定；用户暂停/恢复时把新状态写回 `ui.auto_scroll`，作为下次进入房间的初始值。
3. 独立礼物栏（`separate` 模式）各自维护跟随状态，互不影响。
4. 「回到最新」使用平滑滚动。
5. `visibilitychange` 为 hidden 时不依赖 rAF（后台会被节流），改为 1s 定时批量写入 store，恢复可见时立即 flush 并对齐滚动。
6. **可视高度变化要重新贴底**：弹出面板展开/收起、窗口缩放、礼物栏开合都会改聊天区高度（`ResizeObserver` 监听滚动容器）。跟随模式下重新定位到末尾，否则最新弹幕会被挤出视口（`docs/ui.md` §2.3 的「不遮挡最新弹幕」）；暂停状态下不动视口。
7. **内容不足视口高度时整体贴底**：直播弹幕自下往上读，最新一条应紧贴输入区上方（官方聊天栏同样贴底），因此富余空间留在**顶部**、不留底部。实现是滚动容器 `display: flex; flex-direction: column`、内层虚拟高度块 `margin-top: auto`——**不用** `justify-content: flex-end`：在滚动容器上用 flex-end，内容一旦超过视口高度，顶部会被顶出可滚动区间（滚不回去，flex + overflow 的经典坑）。虚拟行是 `position: absolute` + `translateY` 定位，不受这层对齐影响。

### 7.3 滚动锚定

| 变更类型 | 锚定方式 |
|---|---|
| 尾部追加新消息 | 保持 `scrollTop`；跟随模式下在帧末尾定位到底部；非跟随模式不做位移 |
| 过滤条件变更 | 记录变更前首个可见行的 `local_id` 与其视口偏移，变更后 `scrollToIndex(key, { align: 'start' })` 并按偏移微调 |
| 合并把 N 行折叠为 1 行 | 同「过滤条件变更」，锚点取合并行首条消息的 `local_id` |
| 字体档位变更 / 抽屉开合 / 宽度变化 | 清空高度缓存并重新测量，锚定行保持视口内位置 |
| 手动刷新重连 | 不改变 `scrollTop`，不重排列表（会话缓冲未变） |
| 跟随模式定位 | 直接设置 `scrollTop = scrollHeight`，不使用平滑滚动 |

### 7.4 「回到最新」按钮

| 项 | 规则 |
|---|---|
| 显示条件 | 状态为 `paused` 且新消息计数 ≥ 1 |
| 文案 | `N 条新消息 · 回到最新`，N > 999 显示 `999+` |
| 位置 | 桌面：聊天流右下角；窄屏：输入区上方，水平居中 |
| 层级 | 浮于列表之上，不参与虚拟列表布局，不占行 |
| 点击 | 恢复 `following`（§7.2）并按规则 4 定位 |

## 8. 过滤、样式与合并

### 8.1 过滤（`filter.*`）

| 维度 | 偏好键 | 形态 | 匹配规则 | 求值顺序 |
|---|---|---|---|---|
| 消息类型 | `filter.kinds` | 六种 `kind` 多选白名单 | 未列入白名单的 `kind` 不渲染、不参与合并 | 1 |
| 系统通知 | `ui.system_notice` | 布尔 | 关闭时 `system` 行一律不渲染（见 §4.8） | 2 |
| 粉丝牌等级 | `filter.medal_level_min` | 数值下限（0 不限） | `medal_level` 小于该值的消息丢弃；阈值 > 0 时无牌（`medal_level == 0`）消息一并丢弃 | 3 |
| 用户 | `filter.uids` | UID 屏蔽列表 | 精确匹配 `uid`；`uid == 0` 的游客不参与匹配 | 4 |
| 关键词 | `filter.keywords` + `filter.keywords_mode` | 关键词列表 + 模式 | 对 `content` 做 Unicode 大小写折叠后子串匹配；多个关键词之间为 OR；`hide` 命中即丢弃，`only` 未命中即丢弃 | 5 |

求值顺序固定为 1→5，通过后进入合并（§8.4）再进入虚拟列表。第 3 步只作用于 `danmaku` / `gift` / `guard`；`superchat` / `interact` / `system` 不受 `filter.medal_level_min` 影响。

- 付费消息保底：`superchat` 与 `guard` 在类型白名单中的开关**必须**保留在设置面板上，但允许用户取消；取消后列表顶部显示一次性提示条「已隐藏付费消息」，可撤销。
- `filter.kinds` 为空数组时列表恒为空，显示「全部消息被过滤」空态并提供「恢复全部类型」按钮（写回六种 `kind` 全集）。
- `ui.gift_panel_mode = separate` 时，`gift` / `guard` 的渲染位置变为礼物栏，但白名单语义不变（移除即两处都不渲染）。
- 关键词告警：`filter.keywords_alert = true` 时，命中关键词的消息高亮并在命中时提示（契约 §8），隐藏模式同理只作用于命中项。

### 8.2 字号

`ui.font_scale` 为 number，范围 0.8–2.0，默认 `1.0`。滑杆给出四个命名预设（不引入额外键名）：

| 档位（预设） | `ui.font_scale` |
|---|---|
| 紧凑 | 0.86 |
| 标准（默认） | 1.00 |
| 舒适 | 1.14 |
| 大 | 1.29 |

所有字号 = 标准档基准（body 的 `--fs-root`，14px）× `ui.font_scale`。实现上**不给每处写 px**：弹幕区与各个面板把 `ui.font_scale` 写成 `em` 落在容器上，其余字号一律走 `--fs-1 … --fs-8` 的 em 令牌（§9.2）——所以滑杆能一路作用到时间戳、昵称、徽标与表情尺寸（用户 2026-09-12：字号要同步调整表情尺寸）。滑杆取非预设值时不吸附到预设。变更后清空高度缓存并按 §7.3 重建锚点。

### 8.3 消息弱化与主题

| 对象 | 默认不透明度 | 说明 |
|---|---|---|
| `danmaku` / `gift` / `superchat` / `guard` | 1.0 | 正文不透明 |
| `interact` | 0.6 | 弱化；另受 §4.8 的自动消失控制 |
| `system` | 0.7 | 弱化、居中；默认不渲染（§4.8） |

> 整表不透明度（原 `ui.opacity` 滑杆）**已删除**：用户 2026-09-12 反馈那条实现方式不是预期，
> 重新设计前不再提供该设置（见 `docs/roadmap.md`）。上表是每种 `kind` 的固定视觉档位，不是可调项。

主题由 `ui.theme` 决定，取值 `system` / `dark` / `light`，默认 `system`；六种 `kind` 的颜色 token 在明暗两套取值下分别定义，切换主题即换 token，不改变 `kind` 语义。

### 8.4 合并相似消息

由 `ui.merge_similar`（默认 `true`）开关，窗口基准值为 `ui.merge_window_ms`（integer，默认 `8000`）。各 `kind` 的窗口 = 基准值 × 下表倍率，倍率为本地渲染规则，不占独立偏好键。

| kind | 合并键 | 窗口倍率 | 默认窗口（基准 8000ms） | 合并后展示 |
|---|---|---|---|---|
| `danmaku` | room + uid + uname + medal_name + medal_level | ×1 | 8s | `昵称：内容 ×N（首末时间）[展开]` |
| `gift` | room + uid + 礼物名 | ×2 | 16s | `昵称 投喂 礼物 ×N 共 amount`（连击聚合） |
| `superchat` | 不合并 | — | — | 每条独占卡片 |
| `interact` | room + uid + 行为类型 | ×1 | 8s | `N 人进入直播间` 同行聚合 |
| `guard` | room + uid | 不合并 | — | 每条独立，避免掩盖开通事件 |
| `system` | room + cmd 派生描述 | ×4 | 32s | `—— 描述 ×N ——` |

实现规则：

1. 合并只在「尚未被虚拟列表消费的入队消息」与「当前最后一行」之间进行，不回溯修改视口上方的历史行。
2. 合并后行数减少，行高按 §7.1 重新测量，锚定按 §7.3 恢复。
3. 「展开」把合并行还原为独立行（会话内有效，不写回偏好）；展开后该行不再参与后续合并。
4. `ui.merge_similar = false` 时全部按原始行渲染；`ui.merge_window_ms` 仅在启用时生效，修改后只对后续合并生效。
5. 合并计数 `N` 显示上限 999，超过仍显示 999（计数本身不封顶）。

### 8.5 筛选与显示面板（工具行「筛选」）

房间页不再有常驻的一整行控制条（用户 2026-09-12：「筛选功能全部列到展开菜单中」）。所有筛选与显示开关都在输入区上方的**筛选面板**里，分三块：

| 分区 | 内容 | 相关键 |
|---|---|---|
| 消息类型 | 六种 `kind` 白名单（`filter.kinds`，全选=不过滤） | `filter.kinds` |
| 关键词 | 关键词输入（空格分隔）、模式（命中隐藏 / 仅显示命中）、命中高亮 | `filter.keywords` / `filter.keywords_mode` / `filter.keywords_alert` |
| 显示 | 字号滑杆、**时间戳开关**、互动消息自动消失、系统通知、合并相似、礼物栏模式 | `ui.font_scale` / `ui.show_timestamp` / `ui.interact_auto_hide` / `ui.system_notice` / `ui.merge_similar` / `ui.gift_panel_mode` |

| 时间戳开关 | 规则 |
|---|---|
| 键 | `ui.show_timestamp`（契约 §8，boolean，默认 `false`） |

| 关闭 | 整列不渲染（行从徽标/头像开始），不是渲染成空白 |

账号相关（登录态 / 多账号切换 / 新增 / 删除 / 扫码 / 登出）在**房间列表页的账号管理对话框**（§2.2.1），不占房间页空间。
其余键的读写仍走 `prefs_get` / `prefs_set`（写接受部分键值补丁，未知键或非法值返回 `BAD_REQUEST`）。
「手填 Cookie」是需求 §2.5 的三种登录方式之一，因此界面**提供**输入框（§2.2.1，密码型、折叠在高级入口里）：
值只进一次 `account_login_cookie` 调用，界面任何地方都不回显、不保存；改 `config.toml` 仍是一条等价的旁路（契约 §4.1）。

## 9. 宽窄屏形态（断点与设计令牌）

用户 2026-09-12：界面要能**缩到竖屏（手机比例）**，后面要上安卓；同时全局风格要成体系、不然样式散在各处硬写。
这一节是排布与令牌的唯一口径，样式实现全在 `apps/desktop/ui/src/app.module.css`。

### 9.1 断点与形态对照

同一套 DOM，只有排布随宽度变。断点是 **520px**：> 520px 是宽屏（桌面），≤ 520px 是窄屏（竖屏）。
**竖屏是默认形态**（用户 2026-09-12：窗口默认尺寸 390×844，见 `apps/desktop/src-tauri/tauri.conf.json`），宽屏是适配；
排版的**第一优先**因此是窄屏，宽屏是同一套排布在更宽容器里的自然结果。
窄屏的验证视口取**窗口最小宽度 360×844**（可达面的边界值，§15），不是 390：390 只是常见值，
排版在 360 撑不住的话，把窗口拖到最小的人就会看到它碎掉。

| 区域 | 宽屏（> 520px） | 窄屏（≤ 520px） |
|---|---|---|
| 房间列表页 | 单列、居中、左右留白 24px | 单列，左右留白 12px |
| 房间头 | 一行：返回 · ●状态 · 标题 ··· 在线 / 看过 / 电池 · `⋯` | 同一行结构，但允许**换行**；任何宽度下**不许横向滚动** |
| 弹幕列表 | 唯一生长区与滚动区 | 同左 |
| 弹出面板（表情 / 短语 / 筛选） | 文档流里的一块，向上展开，只挤压列表（不遮最新一条）；限高 `--panel-max-h` = 260px | **同一口径**：也在文档流里，只挤压列表、不遮最新一条；区别只在限高——窄屏用视口份额 `--panel-max-h-narrow` = **45vh**（844px 下 ≈ 380px），内容超出由**面板内部滚动**承担，不去吃列表空间。面板头常驻「关闭」按钮 |
| 房管面板 | 同弹出面板（文档流、只挤压列表、限高 260px） | 同弹出面板（文档流、限高 45vh、内部滚动、有「关闭」） |
| 账号管理对话框 | 居中卡片（`max-width: 680px`），顶对齐，点背景或 `Esc` 关闭 | 贴底 sheet：占满宽度、顶部圆角、内容可滚动、头部「关闭」。它是**模态流程**（不是在读弹幕时顺手展开的面板），所以这里用覆盖式而不是挤压 |
| 输入区 | 输入框占满宽度，工具行一行放得下 | 输入框占满宽度；工具行**放不下就换行**，不挤成小方块 |
| 礼物 / SC 折叠条 | 输入区下方一行 | 同样一行，不换行，不挤掉弹幕列表 |
| 触屏热区 | 不强制 | 窄屏下面板 / 账号对话框（自底 sheet）里的可点元素（按钮、输入框、下拉、复选框的 `label`）高度 ≥ **40px**（`--tap-min`）；复选框与滑杆本体不撑高（会变形），热区由它们的 `label` 承担 |
| 行内菜单入口 | 无（只有右键 / 长按，见 §4.5） | 无（同一个入口） |

**窗口的最小宽度 = 360px**（`apps/desktop/src-tauri/tauri.conf.json` 的 `minWidth`；`minHeight` 仍是 480）。
这条是**可达性**约定，不是样式：断点 520px 决定「拖到多窄会变窄屏形态」，最小宽度决定「用户能不能拖到那里」——
把窗口拖到 **360–520px** 之间就是窄屏形态，桌面端可自查（用户 2026-09-12 实测：原先 `minWidth: 720`
把窄屏形态整块挡在门外，界面上怎么拖都到不了）。安卓端将来复用同一套断点与令牌，不另开一套样式。

**窄屏的面板为什么也是「挤列表」**（用户 2026-09-12 定案）：issue #8 里就写过「下方菜单展开时自动把弹幕区域往上弹，不要挡住最新的弹幕」，桌面端一直照这个做；窄屏一度改成覆盖式 sheet 省空间，代价是最新一条被盖住，用户选了「挤列表」。于是两个视口的差别只剩**限高的算法**：宽屏固定 260px，窄屏用视口份额 45vh（≈380px），超出由面板内部滚动承担，列表仍剩三分之一以上。**短语面板与表情面板是这条里的例外**：两者都在自己内部再分「固定行 + 可滚区」——短语是「面板头 + 加一条」固定、芯片区滚（§6.2），表情是「面板头 + 分组 tab」固定、表情格滚（§6.3）。理由分别是「加短语那一行不许被顶走」与「切组的 tab 不许被滚走」，共同点是**这两样都是入口，不能因为内容变多就消失**。**账号对话框**是模态流程，不受这条约束，保持自底 sheet。

因此宽屏那两条口径（`layoutOnlyChatShrank` 只挤列表、`layoutNewestNotCovered` 不遮最新一条）在**两个视口都是断言**，没有例外名单（§15）。另外，面板展开会改可视高度，用户自己滚上去看历史时**正在看的位置不能被弹走**（`layoutPanelScrollStable`：停在中间 → 展开 → 同一行在视口里的位移 < 8px）；跟随模式下重新贴底是有意的（`MessageList` 的 `ResizeObserver`）。

### 9.2 设计令牌表

颜色、间距、圆角、字号、阴影只有一处定义：`app.module.css` 顶部的 `:root`。组件规则一律引用令牌，`index.css` 只放全局重置与元素默认样式、不再定义任何值。改主题色或改一档间距 = 改一处。

| 类别 | 令牌 | 取值 | 用法口径 |
|---|---|---|---|
| 间距阶 | `--sp-1 … --sp-5` | 4 / 8 / 12 / 16 / 24 px | 间距只从这一档取；**弹幕行内只允许 `--sp-1`（贴）与 `--sp-2`（分）**（§4.1） |
| 圆角阶 | `--r-1 … --r-4`、`--r-full` | 4 / 8 / 12 / 16 / 999 px | 小控件 `--r-1`、卡片 `--r-2`、对话框 `--r-3`、sheet 顶部 `--r-4`、正圆与胶囊 `--r-full` |
| 字号阶 | `--fs-1 … --fs-8` | 0.79 / 0.86 / 0.93 / 1 / 1.07 / 1.15 / 1.3 / 1.43 em | **全部是 em**，不能写成 px：基准字号由 body 的 `--fs-root`（14px）与弹幕区 / 面板上的 `ui.font_scale`（写成 em）共同给出，因此字号滑杆能作用到所有文字（§8.2） |
| 颜色语义槽 | 背景 `--bg`；表面 `--bg-elevated`；下沉面 / 输入 `--bg-input`；分隔线 `--border`；正文 `--fg`；次级文字 `--fg-dim` / `--fg-muted` / `--fg-subtle`；强调 `--accent`；成功 `--ok`；警告 `--warn`；错误 `--danger` | 见 `:root` | 主题色只在这里；`--on-accent` / `--on-ok` / `--on-danger` 是彩色底上的文字色，遮罩 `--overlay`，悬停洗色 `--hover-wash` |
| 徽标底色 | `--gold`、`--neutral`、`--guard-1…3`、`--sc-1…5`、`--block-platform`、`--block-room`、`--badge-fg`、`--badge-lift`、`--badge-border` | 见 `:root` | 粉丝牌**不吃**这些：它的真彩色来自上游（§4.2），令牌只兜底 |
| 阴影 / 遮罩 | `--shadow-menu`、`--shadow-dialog`、`--shadow-sheet`、`--overlay` | — | 菜单 / 对话框 / sheet / 遮罩各一处 |
| 行与触屏的固定尺寸 | `--row-line`、`--avatar` = 0.9×行盒、`--badge-h` = `--avatar`、`--emote` = 1.1×行盒、`--time-col`、`--tap-min`、`--panel-max-h`、`--panel-max-h-narrow`、`--sheet-max-h` | — | 只有这些是「结构尺寸」；其余一次性尺寸（二维码 200px、菜单最小宽 150px 等）仍写在各自规则里，不硬凑进间距阶。`--panel-max-h-narrow` 用视口份额（45vh）而不是固定像素，窄屏才不会被面板吃掉整屏。**弹幕行的那四个是一组**：`--row-line` 是基准（正文行盒高，1.5em，声明在 `.row` 上并用 `@property` 注册成 `<length>`，这样它算成 px 后再往下继承，子元素各写各的字号也不会算错），**而 `--avatar` 有两层**：`.row` 里是行盒的 0.9 倍，`:root` 里另给一个行外默认值（1.35em，随所在字号走）——`.avatar` 是跨页面复用的组件（关注列表 / 账号区 / 账号对话框都在弹幕行之外），令牌只活在 `.row` 里会让那些地方 `var(--avatar)` 解析失败、`<img>` 退回原图尺寸（2026-09-12 的返工，见 §15），头像 / 徽标 / 表情三个尺寸都从它按比例派生（§4.1） |

浅色主题（`ui.theme`）**不是第二套样式**：只在 `:root[data-theme="light"]` 里给这些槽位换一组值，组件规则一行都不用改。新增样式时不得再写字面颜色 / 间距 / 圆角 / 字号——要新值就先加令牌。

**关于「挤了怎么办」的一条规矩**（用户 2026-09-12 定案）：弹幕行的行高是 **内容 + `--sp-1`（4px）上下内边距 ≈ 29px**（原来是 23px），这是为了让行与行在触屏上分得开；代价是同样高度少看几行——面板展开时弹幕列表约剩一半（360×844 下约 390px ≈ 13 行 @29px），面板内容超出则走面板**内部滚动**，不靠遮挡换空间。如果将来真觉得挤，**正确的做法是新增一档「紧凑」令牌**（例如 `--sp-0: 2px`，并在令牌表里写清它只用于哪一类场景），**不是**就地把某个 `--sp-1` 改成 `2px`：间距阶的价值就在于「以后不用微调」，破一次例就等于给下一个人留了口子。

## 15. 自检：房间页无头冒烟

布局这类「排得对不对」的规则靠人工目视不可靠，因此有一份可重复跑的无头冒烟：真实的 `dist` 产物 + 注入的 `__TAURI_INTERNALS__` 替身（假 IPC、假样本），跑完整房间页并断言几何与副作用。**它有两个引擎**：Chromium（默认）与 WebKit（`--engine webkit`）——后者就是 macOS 上 Tauri 用的 WKWebView，**宿主引擎必须在验证链里**。

```bash
cd apps/desktop/ui
npm run build
node smoke/run-headless.mjs                    # Chromium（默认）：自己起 Chrome for Testing 走 CDP
node smoke/run-headless.mjs --engine webkit    # WebKit（宿主引擎）：Playwright，同一份场景 / 同一套断言
```

**两个视口**：1440×900（宽屏）与 **360×844**（窄屏：竖屏是默认形态，而 360 是窗口能达到的**最小宽度**，即可达面的边界值）。用 CDP 的 `Emulation.setDeviceMetricsOverride`
把布局视口改小，跑的是**同一份场景代码**——窄屏那遍不是另写一套脚本，否则两边会各自漂移。

**运行器自己不添乱**（2026-09-12 补）：① **每一步都有超时** —— 每个 CDP 调用、连调试端口、导航、起浏览器各有一档上限，超时即报错并说清卡在哪条命令（曾经出现过「机器同时挂着十几个残留浏览器、渲染进程不产帧」的状态：进程活着、端口连得上，但命令永不回复，脚本于是「一行输出都没有」地挂死）；② **退出必收自己的浏览器** —— 正常退出、断言失败、未捕获异常、`SIGINT`/`SIGTERM`/`SIGHUP` 都会杀掉自己起的进程组与全部后代，启动前还会清掉上一次的孤儿（只认我们自己的标记、且只杀 ppid==1 的遗留物，不碰用户自己的 Chrome）——不清理的话，验证本身就会把环境搞坏（那次漏了 19 个，机器内存只剩 28MB）；③ **浏览器候选依次自检** —— `CHROME_BIN` → omp 自带的 Chrome for Testing → 系统 Chrome，起一台就拍一张 `about:blank` 验它**真的会产帧**，不合格就换下一个（浏览器能不能渲染是环境事实，不是常量）；④ **截图是证据不是断言** —— 产不出帧时告警并跳过，不把一轮好好的断言跑死（末尾会汇总张数）。

**同一台机上冒烟必须串行：一次只让一个浏览器跑**（不管是谁在跑）。并发跑两份浏览器时，内存压力下**系统会先杀掉 WebKit 的 WebContent 进程** —— 表现是 `page.evaluate: Target crashed`，而且**会伪装成「某一段场景必崩」**：今天这个假象骗了两个人（一个以为是表情面板那段代码，一个以为是自己的改动）。2026-09-12 实测：同一份夹具同一次运行里，第一次崩、换一张新页重试就把表情面板 / 房管 / 账号全部跑过 —— 所以**单次崩溃不等于该场景必崩**。

配套的两条硬规矩：① **崩溃要重试，但要有上限（1 次）并记账** —— 日志写清「第几次尝试、是首次还是重试」，重试必须**重跑整个场景**（断言一起重跑，不是只补截图），两次都崩才报失败，且失败信息要说明「这是环境问题（内存压力），不是断言不成立」；② **跨进程的等待都要有超时**（见上一条「运行器自己不添乱」），否则一次环境抖动就会变成「脚本挂了、什么都不说」。

**宿主引擎的旁证链路**：Playwright 的 WebKit 只是 WebKit 的一个构建，**系统 WKWebView 才是宿主本尊**（Tauri 在 macOS 上用的就是它）。因此另有一条零构建差异的链路，跑的是同一个冒烟页、同一份快照：

```bash
cd apps/desktop/ui
npm run build && node smoke/room-page.mjs            # 生成冒烟页（默认 /tmp/danmubox-ui-smoke.html）
swift smoke/wkwebview-host.swift /tmp/danmubox-ui-smoke.html "$TMPDIR/wk-host" 1440 900 wide
swift smoke/wkwebview-host.swift /tmp/danmubox-ui-smoke.html "$TMPDIR/wk-host" 360 844 narrow   # 可达面边界值
node smoke/run-headless.mjs --from-snapshot "$TMPDIR/wk-host/snapshot.json"                      # 同一套断言判定
```

它的已知局限（所以它是旁证、不是主闸门）：**没有显示会话时 rAF 没有持续帧** —— 2026-09-12 实测 `requestAnimationFrame` 在 2.2s 里只触发 **1** 次（首帧），而 `setTimeout` 正常。后果是「跟随最新 / 虚拟列表窗口」这类**按帧推进**的断言会假失败：同一份快照交给 `--from-snapshot` 判定，**退出码是 1，213 条里有 24 条不成立**，全部是这类（`row*` / `layoutNewest*` / `layoutFollowing*` / QR 轮询那一条）；而**几何 / 尺寸 / 溢出 / 颜色**那一类（`listAvatarsSized`、`listAvatarBoxes`、`narrow_listNoHorizontalScroll`、`rowScale`…）成立 —— 这正是它存在的意义：**宿主引擎上的尺寸与布局证据**（这次根因 `--avatar` 就是靠它钉死的）。工具自己会把这句局限打在 stderr 上，别把这里的失败读成产品问题。每次只跑一个视口；完整断言一律以 `run-headless.mjs --engine webkit` 为准（Playwright 的 WebKit 有持续帧，516 项全绿）。

**两个引擎**：Chromium 与 WebKit 各跑一遍同一份场景代码、同一套断言（不是两套脚本），视口也一样。为什么要两个：**应用跑在 macOS 的 WKWebView 里，Chromium 的绿只证明「在 Chromium 里成立」**。两边的差别是真实存在的（`@property` 注册自定义属性、网格的 `minmax()`、`em` 的求值时机），但也**不要**把所有问题都归给引擎——见下面 2026-09-12 的第二个反例。跑 WebKit 需要一次性的 `npm i -D playwright && npx playwright install webkit`（后者约 80MB，落在 `~/Library/Caches/ms-playwright`）。

**判据：视口是产品的可达面，不是测试的自由参数。** 凡新增「只在某些视口成立」的行为，必须同时确认**用户能到达那个视口**——
窗口/设备的最小尺寸、断点、以及入口（能不能拖到、能不能旋转到）。2026-09-12 的反例：窄屏形态在无头浏览器的视口里全绿，
而桌面窗口的 `minWidth: 720` 让用户永远够不到它（`tauri.conf.json` 现已钉在 360px，§9.1）。落地两条：
① 新增按视口分叉的行为时，先确认窗口/设备可达该视口；② 够不到就在报告里明说「该形态仅在某些视口成立、当前入口够不到」，
不许当成已验证。

**判据：渲染引擎同样是可达面，而且「夹具能不能暴露失败」也是一条判据。** 2026-09-12 的第二个反例：弹幕行重做把
`--avatar` 等尺寸令牌从 `:root` 挪进了 `.row`，于是 `.row` 之外的共用组件（关注列表 / 账号区 / 账号对话框的头像）
`var(--avatar)` 解析不出来，`width` 落到 `auto`，`<img>` 按**原图尺寸**渲染（上游头像是原图直出，512 见方）——
装到真机上主页只剩下一个头像的角落。三条落地：
① 冒烟引擎必须覆盖宿主引擎（上面的 `--engine webkit`）；
② 共用组件（`Avatar.tsx` 这类跨页面复用的）消费的令牌必须能解析出值，不能只活在某个组件的作用域里；
③ **夹具要能失败**：原来的样本把关注项头像写成空串、账号头像用 32×32 小图，`auto` 尺寸在小图上看着无害，
所以两个引擎都是绿的——现在夹具用**原图尺寸 512×512**，并断言列表页头像的渲染尺寸（`listAvatarsSized`）。
这个反例同时说明：**先怀疑引擎，但要用证据落地**——它的根因与引擎无关（修前修后两个引擎行为完全一致）。

| 项 | 规则 |
